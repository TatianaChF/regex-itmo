Валидация email: уязвимый и надёжный regex

Уязвимое регулярное выражение: /^([a-zA-Z0-9_.-]+)+@([a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$/

Надежное регулярное выражение: /^[a-zA-Z0-9_-]+(\.[a-zA-Z0-9_-]+)*@([a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$/

Строка для проверки: "a"×30 + "!" — совпадение невозможно (рассматриваем худший случай)

Внизу вы увидите кнопки и таймер. Кнопки запускают проверку регулярного выражения, а таймер внедрен для демонстрации блокировки кода во время проверки регулярного выражения. После выполнения выводится: время проверки в миллисекундах, количество тиков (1 тик = 100 мс) на момент запуска и сравнение «сколько тиков сработало за время проверки / сколько должно было». Если регулярное выражение уязвимо, счетчик замирает: за время проверки не срабатывает ни один тик, хотя по времени должно было пройти несколько десятков — это и есть доказательство блокировки основного потока.

Проблема уязвимого регулярного выражения — вложенный квантификатор (X+)+. Последовательность одинаковых символов можно разбить на группы многими способами: для строки длины n их 2ⁿ⁻¹ (например, aaa → [aaa], [a][aa], [aa][a], [a][a][a]). Тестовая строка никогда не совпадёт (после локальной части обязан идти @, а стоит !), но движок узнает об этом, лишь перебрав все разбиения — сложность O(2ⁿ).

У надёжного регулярного выражения локальная часть переписана: первый кусок [a-zA-Z0-9_-]+ (без точек), а каждое следующее повторение группы (\.[a-zA-Z0-9_-]+)* обязано начинаться с литерала .. Значит, границы повторений могут проходить только там, где в строке реально стоит точка — разбор однозначный, перебирать нечего. На той же строке время линейное O(n), доли миллисекунды. Доменная часть у обоих выражений одинаковая и безопасная: каждое повторение группы ([a-zA-Z0-9-]+\.)+ обязательно заканчивается точкой, не входящей в класс, поэтому границы повторений также однозначны.

Тиков таймера (каждые 100 мс): 0
